# B2B LP Copy (日本語版)

法人向けのページで刺さらない原因は、ほとんどの場合、文章ではない。誰に読ませるか、何を売るか、何を言わないかが決まっていない。このスキルはその3つを先に固め、文言はいちばん最後に触る。

## なぜ文体スキルだけでは直らないか

文体スキルは「書き手の不在」を直す。LPで欠けているのは書き手ではなく、読者と売り物の骨格である。初期案が短文で、名詞句見出しで、ダッシュもなく、文体チェックを全部通っているのに問い合わせが来ない、という状態はここから生まれる。AI臭くはないが売れない文は、文体スキルが仕事をした結果として出てくる。

さらに、文体スキルの一部の指示はセールスコピーと衝突する。毒や皮肉を残す、中間温度（まあまあ、微妙）を混ぜる、命題型見出しを避ける。これらは記事には効くが、B2Bのページでは信頼を削る。文体スキルに渡した後、この衝突を最後のチェックで打ち消す。

## 手順

この順で進める。飛ばすと、後の工程で直せないずれが残る。

### 1. 入力を揃える

書き始める前に、次の3つが手元にあるか確認する。ないものは書く前に依頼者に求める。

- 想定読者の一覧（役職と、その人が抱えている課題）
- 売り物の一覧（プラン、価格、提供範囲、納品物）
- 参照文書（プレスリリース、既存の提案書、料金表など、先に確定している文章）

3つのうち想定読者と参照文書が欠けたまま書き始めた初期案は、ほぼ確実にずれる。文章技術で埋まる欠落ではない。

### 2. 読者×主張表を作る

想定読者を縦に、ページのセクションを横に並べる。各読者について「これを信じれば問い合わせる一文」を先に書き、その一文がどのセクションで示されるかを表に埋める。

空欄の読者がいれば、その読者はヒーローかCTAで落ちている。ヒーローコピーは、想定読者の過半数が自分の話だと読める抽象度に置く。用途を一つに絞ったヒーロー（例：社内交流だけ）は、他の読者を最初の画面で失う。

表の作り方と例は `references/reader-claim-matrix.md` を読む。

### 3. 言えないことリストを先に作る

提供側が解決できない課題、未検証の効果、実績の不在、まだ決まっていない条件を列挙する。各項目に次のいずれかを割り当てる。

- 触れない（その課題を示唆する語も使わない）
- 限定表現にする（「応募が増える」ではなく「入社前に会社を体験してもらう」）
- 交換条件に変える（実績ゼロ → 先行導入の割引と代表の直接関与と事例化依頼）

隠す、は選択肢に入れない。法人の担当者は隠されたことに気づいたとき、そのページの他の主張も信じなくなる。誠実さはここでは演出ではなく、説得の道具である。

変換パターンは `references/claims.md` を読む。

### 4. 参照文書との差分を取る

プレスリリースや提案書があれば、そこから次を抜き出す。

- 一本の筋（リリースの見出しにある置き換え、例：説明する施策を体験する施策へ）
- 提供内容の一覧（プラン数、価格、オプション、納品物）
- 特徴として書かれている項目

ページ側に欠けているセクションと数字を洗い、一致させる。リリースに3プランあってページに2プランしかない、リリースに特徴が3つあってページに特徴セクション自体がない、といったずれはこの段階で見つける。

### 5. セクションごとの役割を一文で決める

各セクションについて「このセクションは何をする場所か」を一文で書く。書けないセクションは削る。標準的な役割と順序は `references/section-roles.md` にある。要点だけ挙げる。

- 課題：読者が自分を見つける場所。一行に一読者。
- 場面：誰の課題かが語順の先頭に来る。
- 特徴：なぜ他社でなくここか。参照文書の特徴をここに落とす。
- 実績：数字そのものより、その数字が何を証明するかを添える。
- 料金：直前に根拠（実績、先行条件）を置く。割引の理由を価格より先に読ませる。
- 進め方：読者が次に何をすればいいかが分かる語で書く。
- FAQ：読者が上司に報告するときに使える答えを入れる（納品物、期間、権利、効果の確認方法）。

### 6. 分からないことは書かずに聞く

効果測定の可否、初期顧客への条件、読者の優先順位、注力する用途。提供側の判断が要るものは仮置きせず、質問リストにして返す。

質問は3つ以内に絞り、それぞれ「答えによってどのセクションがどう変わるか」を添える。答えがなくても書ける部分は先に出す。

### 7. ここで初めて文言を直す

ここまでで骨格が決まっている。文言で触るのは次の程度で、全体の2割を超えない。

- 読者が使う語に合わせる（絵 → イラスト、eng → エンジニア）
- 断定に範囲を付ける（覚えている → 半年後も覚えている）
- 一文に一読者、一文に一主張
- 数字には「それが何の証明か」を添える

終わったら文体スキル（stop-ai-slop-jp など）に渡す。

## 最終チェック

文体スキルを通した後に、上から順に確認する。文体スキルの影響で入りがちなものを打ち消す項目を最後に置いてある。

### 読者と主張
- [ ] ヒーローコピーを、想定読者の過半数が自分の話だと読めるか
- [ ] 想定読者全員に、着地するセクションがあるか
- [ ] 各読者の「信じれば問い合わせる一文」が、ページのどこかに書かれているか

### 言えないこと
- [ ] 提供側が解決できない課題を示唆する語（応募が増える、売上が上がる、離職が減る）が残っていないか
- [ ] 未検証の効果を断定していないか
- [ ] 実績の不在を隠さず、交換条件に変えているか
- [ ] 割引や特別条件の根拠が、その条件より前に書かれているか

### 骨格
- [ ] 参照文書のプラン数、価格、特徴の数と一致しているか
- [ ] 役割を一文で言えないセクションが残っていないか
- [ ] 数字に「それが何の証明か」の一文が付いているか
- [ ] 読者が上司に報告するときに使える一文（納品物、レポート、期間）があるか
- [ ] 進め方の各ステップで、読者が次にすることが分かるか

### 文体スキルとの衝突
- [ ] 「まあまあ」「微妙」「悪くない」がセールスコピーに混入していないか
- [ ] 皮肉や自虐が、信頼を削る位置に残っていないか
- [ ] ヒーローとCTAの見出しが、名詞句に丸められて主張を失っていないか
- [ ] 伝聞（らしい、ようだ）が、自社の提供内容の説明に混ざっていないか

## 採点

4軸を1〜10で採点。合計28/40を下回ったら手順2に戻る。

| 軸 | 質問 |
|---|---|
| 読者 | 想定読者全員が、自分の話だと分かる場所を持っているか |
| 誠実 | 言えないことが、触れない／限定／交換条件のいずれかで処理されているか |
| 骨格 | 参照文書と一致し、各セクションの役割が一文で言えるか |
| 根拠 | 数字と条件に、それが何の証明か、なぜその条件かが添えてあるか |

## 修正の優先順位

時間が限られているなら、上から順に対処する。

1. 読者×主張表の空欄を埋める（手順2）
2. 言えないことの処理（手順3）
3. 参照文書との差分（手順4）
4. セクションの役割と順序（手順5）
5. 文言（手順7）

1と2を直さず5だけ直しても、問い合わせは来ない。
